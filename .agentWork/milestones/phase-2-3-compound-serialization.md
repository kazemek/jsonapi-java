# Phase 2.3 — Jackson 3 Compound Serialization Context

> **Module:** `jsonapi-java-jackson3`  
> **Dependencies:** Phase 2.2  
> **Status:** Not started

## Goal

Add explicit, bounded compound-document inclusion to Jackson 3 write mapping without turning relationship mapping into automatic graph traversal.

## Research and constraints

- [`docs/vision.md`](../../docs/vision.md) — a relationship creates linkage but never requests automatic inclusion; include paths and traversal limits remain explicit application policy.
- [ADR-005](../../docs/adr/005-domain-mapping-and-inclusion.md) — compound serialization validates requested paths, includes intermediates for full linkage, deduplicates by identity, applies finite depth/count limits, treats repeated identity as deduplication not recursion, and emits deterministic first-encounter order. No JPA/Hibernate implicit integration.
- [JSON:API compound documents](https://jsonapi.org/format/1.1/#document-compound-documents) — included resources require full linkage and unique resource identity; `included` appears only when `data` is present; a resource identity must not appear in both primary `data` and `included`.
- `JsonApiDocumentValidator` (core) — already enforces identity uniqueness, full linkage, and local-identifier consistency; the engine's output must pass this validator unchanged.
- Phase 2.2 — `ResourceMapping` / `MappingProperty` / `MappingDefinitionCache` provide the Jackson logical-property metadata and collection content-type resolution reused by traversal; traversal must not rescan domain types. `DomainResourceWriter.toResource` always emits full linkage for every mapped relationship on an already-selected resource; inclusion traversal is a separate concern (see Inclusion behavior).
- Core `RelationshipPaginationKey` (`resourceType` + `relationshipName`) is the shape precedent for typed include allowances; jackson3 may introduce a public `RelationshipAllowance` (or equivalent) with that shape rather than overloading pagination semantics.
- [ADR-009](../../docs/adr/009-jspecify-nullness.md) — new public types are `@NullMarked` with accurate `@Nullable`; [ADR-010](../../docs/adr/010-architectural-tests.md) — no new production package is introduced and the existing jackson3 allowlist (JDK, JSpecify, core public, annotations, `tools.jackson..`) remains unchanged.
- Phase 2.13 (Jackson 2 parity) already mirrors this mapping-only context (no `ValidationContext` on the compound serialization context); keep that milestone in sync if this contract changes further.
- Existing `JsonApiResourceMapper.toDocument(Object, @Nullable DocumentEnvelope)` makes a two-argument `toDocument(Object, CompoundSerializationContext)` overload ambiguous for `toDocument(resource, null)`; compound mapping therefore uses a three-argument shape only.

## Serialization context

The caller supplies an immutable `CompoundSerializationContext` carrying:

- requested include paths as `IncludePath` values (ordered list of relationship JSON:API names; never null — use an empty list for no inclusion request);
- an `IncludePolicy` deciding which relationships may be traversed for inclusion (default `IncludePolicy.denyAll()`);
- maximum relationship depth (default 10);
- maximum included-resource count (default 100).

Defaults request no included resources and apply finite safety limits. The context offers `withX()` copy methods matching the `ValidationContext` style; the constructor and every `withX()` method defensively copy incoming lists and sets (for example `List.copyOf` / `Set.copyOf`, matching the `ValidationContext` precedent) so later caller mutation cannot affect an existing or concurrently used context. The context is a *mapping* concern and does not carry a `ValidationContext` (validation continues to live on `JsonApiDocumentWriter`).

**Limits:** the constructor and `withMaxDepth` / `withMaxIncluded` reject negative values. Zero is valid: `maxDepth == 0` rejects any non-empty include path at pre-validation with `INCLUDE_DEPTH_EXCEEDED`; `maxIncluded == 0` fails with `INCLUDE_COUNT_EXCEEDED` on the first resource that would enter `included` (a requested path that resolves to zero resources may still emit `included: []`).

## Inclusion behavior

- **Pre-traversal validation precedence:** process requested paths in caller order. For each path: (1) compare path length to `maxDepth` (`INCLUDE_DEPTH_EXCEEDED` if longer); (2) walk segments left-to-right, applying the **mapping** check (segment names a relationship on the relevant type via `MappingProperty.jsonapiName()` → `INVALID_INCLUDE_PATH`) then the **policy** check (`DENIED_RELATIONSHIP_INCLUDE`). The first failing check wins; stop before any inclusion-traversal property access. Add a multi-failure test that asserts the winning diagnostic code and exact dotted `propertyPath`.
- **Heterogeneous primary collections:** for `toResourceCollection`, materialize the primary `Iterable<?>` once into an ordered snapshot (for example `List.copyOf` or an equivalent single-pass materialization) before type validation, primary mapping, or inclusion traversal, and reuse that snapshot for all three steps. Do not re-iterate a one-shot or stateful iterable. Validate each requested path against every distinct primary resource type in first-seen snapshot order before any inclusion traversal; within each type keep the depth → mapping → policy precedence above. The winning diagnostic's `resourceClass` is the Java class of the first type that produces the failure. Homogeneous collections are the single-type special case of the same rule.
- **`IncludePath.of(String)` syntax and exception contract:** a valid path is one or more dot-separated non-empty relationship names. Reject empty input, leading or trailing dots, repeated dots, and whitespace-only segments; do not silently trim or otherwise normalize input. Preserve the ordered relationship-name semantics. Factory-time syntax failures throw `JsonApiMappingException` with `MappingDiagnostic.INVALID_INCLUDE_PATH`, `resourceClass == null`, and `propertyPath` equal to the raw input string. Mapper-time relationship-lookup failures (unknown segment on a type) throw the same diagnostic with the owner Java `resourceClass` and a dotted JSON:API `propertyPath`.
- Include intermediate resources required for full linkage along each requested path.
- Emit `included: []` when a supported, explicitly supplied include request resolves to no resources.
- **`included` null vs empty contract:** context-free overloads and a context whose include-path list is empty mean *no inclusion request* — `JsonApiDocument.included` is `null` (member omitted). A context with at least one non-empty valid path that resolves to zero resources is an *inclusion request with an empty result* — `included: []` is emitted. The distinction is "did not ask" (omit) versus "asked but got nothing" (emit `[]`).
- Do not place resources in `included` that were not requested.
- **Policy vs linkage:** `IncludePolicy` governs *inclusion traversal only* — whether a related domain object is read in order to populate `included`. Linkage identifier emission remains Phase 2.2 `DomainResourceWriter.toResource` behavior and is unaffected by `denyAll()` / `allowing(...)`: a denied or unrequested relationship still appears as linkage (its `ResourceIdentifier`) on a selected resource; it is simply never *included*.
- **Access vs linkage:** Primary and included `ResourceObject`s are built with full linkage via `DomainResourceWriter.toResource` (or equivalent), which may read every mapped relationship getter for linkage emission on an already-selected resource. Access-counting and the “never read” guarantee apply only to **inclusion traversal**: reading related domain objects in order to populate `included`. Traversal into a related object happens only when that relationship segment is on a validated, policy-allowed requested path. Off-path relationships are never followed for inclusion and their getters are not invoked for traversal. Access-counting fixtures assert traversal getters, not that linkage getters on primary/included resources are skipped.
- **Output deduplication (separate from traversal):** seed an included-identity tracker with every primary `data` `ResourceIdentity` so a primary resource is never emitted in `included` (self-links and primary-to-primary relationship targets remain linkage-only). Deduplicate `included` entries by `ResourceIdentity` (type+id or type+lid via `ResourceObject.identityKey()`). When a later candidate shares an already-seen included identity, compare with `ResourceObject.equals` (structural record equality); reject with `CONFLICTING_INCLUDED_REPRESENTATION` when `!first.equals(candidate)`. First discovery determines the canonical representation and `included` order.
- **Traversal visit state (separate from output dedup):** track visits by `(ResourceIdentity, request-list index, segment index)` — the request-list index of the `IncludePath` being walked, not `IncludePath` value equality and not segment index alone — so duplicate identical paths in the request list remain independent walks. Discovering an identity for path prefix `a` must not prevent continuing along a longer requested path such as `a.b`; converging paths with different suffixes (e.g. `a.b` and `c.d` meeting on one resource) must still traverse each explicitly requested suffix. Do **not** treat “already present in the included-identity set” as “stop walking this path.”
- Enforce `maxDepth` and `maxIncluded`, failing with `INCLUDE_DEPTH_EXCEEDED` / `INCLUDE_COUNT_EXCEEDED`.
- **`maxDepth`:** a cap on requested *path length* (number of relationship segments from the primary resource along a requested path), not graph diameter. Checked at pre-traversal validation; runtime traversal never exceeds the explicit requested path, so depth is bounded by construction once paths are validated. Exceeding fails with a dotted JSON:API relationship path (e.g. `comments.author`).
- **`maxIncluded`:** enforced across the accumulated included set (not counting primary `data` resources).
- **Order (complete nesting):** iterate primary resources in snapshot / input order as the *outer* loop; for each primary resource, iterate requested `IncludePath`s in caller order as the *inner* loop; within each path, walk relationship targets level-by-level (BFS along that path), iterating to-many target collections in their collection order. Global `included` order is first-discovery across this walk.
- **Diagnostic `propertyPath`:** use dotted JSON:API relationship names consistent with include syntax (e.g. `comments.author`), not only a single Java `logicalName`.

## Safety and ORM neutrality

The mapper has no persistence dependency and never calls JPA/Hibernate initialization APIs. Only **inclusion-traversal** relationship reads are controlled by the inclusion context / `IncludePolicy`; full-linkage construction via `DomainResourceWriter.toResource` may still invoke every mapped relationship getter on a selected resource — including under `denyAll()` — and a lazy proxy or getter may still initialize and trigger I/O. Callers requiring no I/O must provide an access-safe, already-loaded graph. Depth, count, and conflict behavior produce structured `MappingDiagnostic` failures, not unbounded graph walks.

## Deliverables

- Public immutable `CompoundSerializationContext` with `IncludePath` (ordered list of JSON:API relationship names; `IncludePath.of(String)` parses and rejects per the syntax/exception contract above) and `IncludePolicy` (`allowAll()` / `denyAll()` / `allowing(Set<RelationshipAllowance>)` where `RelationshipAllowance` is a public jackson3 record of `resourceType` + `relationshipName`, matching the `RelationshipPaginationKey` shape; **`resourceType` is the JSON:API type of the relationship owner**, not the target type and not a Java class name, matched at every nested include-path segment); `withX()` copy methods and finite defaults (depth 10, count 100); constructor/`withMaxDepth`/`withMaxIncluded` reject negatives and document zero semantics.
- Extend `JsonApiResourceMapper` with unambiguous three-argument overloads only (do **not** add two-argument context overloads that collide with `@Nullable DocumentEnvelope`):
  - `toDocument(Object, @Nullable DocumentEnvelope, CompoundSerializationContext)`;
  - `toResourceCollection(Iterable<?>, @Nullable DocumentEnvelope, CompoundSerializationContext)`.
  Callers without an envelope pass `null` for the envelope argument (`toDocument(resource, null, context)`). The collection overload materializes the primary `Iterable<?>` once into an ordered snapshot and reuses it for type validation, primary mapping, and inclusion traversal. Add internal `CompoundInclusionEngine` that pre-validates paths (precedence and heterogeneous-type rules above), walks the graph for inclusion via selective relationship reads with `(ResourceIdentity, request-list index, segment index)` visit tracking, builds primary and included resources with `DomainResourceWriter.toResource` (full linkage) and uses `extractIdentifier` where linkage-only identity is needed, seeds output dedup with primary identities, allocates all traversal state per mapping invocation, and produces an ordered `List<ResourceObject>` for `JsonApiDocument.included`. Update `buildDocument` to accept `@Nullable List<ResourceObject> included` (`null` = omit the member; empty list = emit `included: []`).
- Add `MappingDiagnostic` codes `INVALID_INCLUDE_PATH`, `DENIED_RELATIONSHIP_INCLUDE`, `CONFLICTING_INCLUDED_REPRESENTATION`, `INCLUDE_DEPTH_EXCEEDED`, `INCLUDE_COUNT_EXCEEDED`, each thrown with `resourceClass` and a dotted JSON:API relationship `propertyPath` where applicable (factory-time malformed paths use `resourceClass == null` and the raw input as `propertyPath`).
- Spock `CompoundSerializationSpec` covering cyclic, shared, conflicting, empty, nested, multi-primary + multi-path, factory-time and mapper-time malformed paths, mixed-type collection validation (including a one-shot primary `Iterable`), nested-policy owner-type matching, limit-exceeding (including zero limits), self-reference / primary-as-related, prefix-overlapping and different-suffix converging paths, concurrent shared-mapper isolation, and multi-failure validation precedence, with explicit include paths; reuse `Article`/`Comment`/`Person` and add access-counting (traversal-scoped), conflicting-representation, and deep-nested test models; assert produced documents pass `JsonApiDocumentWriter` validation (full linkage, identity uniqueness) and `included: []` on empty resolution. Add two richer compound **codec** fixtures (nested-intermediate, shared-identity) under `fixtures/jsonapi-1.1/` with manifest entries, `WriterFixtures` case classes, and `JsonApiDraftSchemaSpec.SCHEMA_KIND_BY_FIXTURE` `"response"` classifications so Phase 2.5's draft-schema cross-check and Phase 2.13 wire parity reuse shared bytes; these fixtures do not replace domain graphs in `CompoundSerializationSpec` (see Test strategy).
- Refresh `jsonapi-java-jackson3/README.md` (minimal usage + agent notes for opt-in inclusion), `package-info.java`, entry-point Javadoc, and `docs/conformance.md` marking compound inclusion **supported** with the exact opt-in policy.

## Non-goals

- Sparse fieldsets; Phase 2.8 adds field selection after inclusion behavior is stable.
- Inclusion defaults hidden in annotations, serializers, persistence providers, or framework adapters.
- JPA/Hibernate initialization APIs, repositories, fetch plans, authorization, or visibility policy; callers own access-safe graph preparation and persistence behavior.
- HTTP `include` query-parameter parsing; Phase 3.1 owns transport syntax.
- Jackson 2 compound serialization; Phase 2.13 owns parity.
- Selective linkage emission (omitting off-path relationships from a resource object's `relationships` member); full linkage on selected resources remains Phase 2.2 `toResource` behavior. No new selective-`toResource` API in this milestone.
- Two-argument `toDocument(Object, CompoundSerializationContext)` / `toResourceCollection(Iterable<?>, CompoundSerializationContext)` overloads (ambiguous with nullable `DocumentEnvelope`).

## Implementation boundaries

- Public types live in `io.github.kazemek.jsonapi.jackson3`; the engine lives in `io.github.kazemek.jsonapi.jackson3.internal`. No new production package; no import of `core.internal` or `com.fasterxml.jackson..`; ArchUnit allowlist is unchanged.
- `CompoundSerializationContext` is immutable and thread-safe: the constructor and every `withX()` method defensively copy incoming include-path lists, `IncludePath` values, and allowance sets (`List.copyOf` / `Set.copyOf`, matching the `ValidationContext` precedent), so later caller mutation cannot affect existing contexts or concurrent mapping. Include-path lists and the context itself are non-null; an empty path list means no inclusion request. `JsonApiResourceMapper` remains safe for concurrent use once created. Existing context-free overloads behave exactly as before (`included` absent / `null`).
- **Per-call traversal state:** the identity tracker, visit state, included count, diagnostics, and ordered included output are allocated per mapping invocation (local state / method-scoped object), never as mutable fields on a shared `CompoundInclusionEngine` instance. Concurrent calls on one mapper must not share traversal state or inclusion limits.
- **Primary collection snapshot:** `toResourceCollection` materializes `Iterable<?>` once into an ordered list before validation and traversal and reuses that snapshot for distinct-type validation, primary `ResourceObject` mapping, and inclusion walks. One-shot or stateful iterables must not be re-iterated.
- Traversal reuses `MappingDefinitionCache`/`ResourceMapping` for relationship content types; it does not reflect independently. To-one and to-many both resolve content type via the same `MappingProperty.accessor().getType()` path already used in `DomainResourceWriter`. Prefer package-visible helpers on `DomainResourceWriter` for content-type / to-many detection reused by the engine; duplicating those two private helpers in the engine is acceptable if elevating visibility is undesirable.
- Include policy is checked per relationship *before* inclusion-traversal property access (owner JSON:API type + relationship name); path membership is checked before reading a relationship property for traversal.
- The engine produces `List<ResourceObject>` (or `null` when no inclusion request was supplied — a context-free overload or a context with an empty path list); `JsonApiDocument` is constructed via `buildDocument` with the populated `included` list when includes were requested (`null` omits the member; empty list emits `included: []`). The writer's aggregate validation runs unchanged; no `sparseFieldsetException` is set by this milestone.
- Files to add: `CompoundSerializationContext.java`, `IncludePath.java`, `IncludePolicy.java`, `RelationshipAllowance.java` (or equivalent public typed key), `internal/CompoundInclusionEngine.java`. Files to edit: `JsonApiResourceMapper.java` (three-argument overloads + `buildDocument(..., included)`), `MappingDiagnostic.java`, optionally `internal/DomainResourceWriter.java` (package-visible helpers only; no selective-`toResource`), `jsonapi-java-jackson3/README.md`, `package-info.java` (public), `docs/conformance.md`, `fixtures/jsonapi-1.1/manifest.json` and new documents, `jsonapi-java-test-fixtures` `WriterFixtures` catalog plus new case classes under `cases/`, and `JsonApiDraftSchemaSpec.SCHEMA_KIND_BY_FIXTURE` (both new fixtures as `"response"`).

## Test strategy

- Cyclic graph: `Article.comments -> Comment.author -> Person` and `Article.author -> Person` with include paths `comments.author` and `author`; assert no infinite recursion, full linkage, first-encounter order, and that off-path relationships are never read **for inclusion traversal** (access-counting fixture scoped to traversal, not linkage getters on selected resources).
- Shared graph: two relationships pointing to the same `Person` included once.
- Conflicting representations: same identity supplied with differing attributes across two paths.
- Empty resolution: include path permitted but resolving to no resources yields `included: []`.
- Nested intermediates: deep path `comments.author` includes the intermediate `Comment` resources required for full linkage.
- Self-reference / primary-as-related: a relationship target that is also a primary `data` identity is not emitted in `included`; document still passes identity-uniqueness validation.
- Prefix-overlapping and converging paths: paths such as `a` and `a.b`, and different-suffix paths such as `a.b` and `c.d` that meet on one intermediate, traverse each requested suffix; first-discovery order and conflict checks still hold.
- Heterogeneous collection: a mixed-type `toResourceCollection` where a path is valid for the first element type but invalid for a later distinct type fails with the later type's Java `resourceClass` and the expected diagnostic. Also cover a one-shot/stateful primary `Iterable` that yields each element only once; assert validation, primary mapping, and inclusion still see the full ordered primary snapshot (no missing resources or reordered primaries from re-iteration).
- Nested policy owner-type: an `allowing(...)` policy that permits a relationship on one owner JSON:API type but not another distinguishes nested segments by owner type.
- Limits: request a path longer than `maxDepth` and a graph that exceeds `maxIncluded`; also cover `maxDepth == 0` / `maxIncluded == 0` and reject negative limits; assert the exact diagnostic code and dotted JSON:API `propertyPath`.
- Invalid paths: factory-time malformed `IncludePath.of(String)` (`""`, `.a`, `a.`, `a..b`, whitespace-only) throws `JsonApiMappingException` with `INVALID_INCLUDE_PATH`, null `resourceClass`, and the raw input as `propertyPath`; mapper-time unknown relationship segment and denied relationship use owner `resourceClass` and dotted `propertyPath`; multi-failure request asserting first-win precedence (depth → mapping → policy per path order, including mixed-type order); assert `INVALID_INCLUDE_PATH` / `DENIED_RELATIONSHIP_INCLUDE` / `INCLUDE_DEPTH_EXCEEDED`.
- Concurrent isolation: two concurrent compound mappings on a shared mapper with distinct graphs produce isolated included sets and do not share visit/count state.
- Round-trip: feed produced documents through `JsonApiDocumentWriter` and assert aggregate validation passes (full linkage, identity uniqueness, lid consistency).
- Canonical codec fixtures: add two richer compound writer fixtures — one nested-intermediate (`comments.author`) and one shared-identity — to `fixtures/jsonapi-1.1/` with manifest entries, `WriterFixtures` case classes, and `JsonApiDraftSchemaSpec.SCHEMA_KIND_BY_FIXTURE` `"response"` entries, so Phase 2.5's draft-schema cross-check and Phase 2.13 wire parity reuse shared bytes. These are codec/model documents, not a substitute for domain graphs in `CompoundSerializationSpec`. The existing single-level `compound-document.json` is retained.

## Acceptance criteria

- [ ] No related resource enters `included` without an explicit include request; nested paths include required intermediates; off-path relationships are not accessed for inclusion traversal (access-counting fixture); first-encounter output order is deterministic; primary identities are never re-emitted in `included`; prefix-overlapping paths still traverse requested suffixes.
- [ ] Deduplication, conflicting representations (`ResourceObject.equals`), cycles, maximum depth, and maximum included-resource count have stable mapping diagnostics and focused tests (including zero/negative limit boundaries, multi-failure validation precedence, mixed-type collections including a one-shot primary `Iterable` snapshot, nested owner-type policy, factory- vs mapper-time path errors, and concurrent per-call isolation); the default context requests no included resources with finite depth/count limits; `@NullMarked` packages with accurate `@Nullable` per ADR-009; the ArchUnit allowlist is unchanged with no `core.internal` or Jackson 2 production dependencies.
- [ ] Generated compound documents pass `JsonApiDocumentWriter` identity/full-linkage/lid validation; the two canonical compound fixtures pass round-trip writer validation; `included: []` is emitted for a context with at least one non-empty path resolving to no resources; context-free overloads and contexts with an empty path list all omit `included`; compound mapping uses only the three-argument envelope+context overloads; different-suffix converging paths still traverse requested suffixes.
- [ ] The canonical `module-docs` checklist passes and `docs/conformance.md` marks compound inclusion **supported** with the exact opt-in policy rather than implying automatic traversal.
- [ ] `./gradlew :jsonapi-java-jackson3:test --tests '*CompoundSerializationSpec'` passes.
- [ ] `./gradlew clean build` passes.
- [ ] Spotless passes (`./gradlew spotlessApply` then `./gradlew spotlessCheck`).
- [ ] Sonar Quality Gate passes; if `SONAR_TOKEN` is unavailable, report Sonar blocked and that CI must still pass the gate.
