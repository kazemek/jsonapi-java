# Phase 2.5 — JSON:API 1.1 Draft-Schema Cross-Check

> **Module:** `jsonapi-java-jackson3` test suite  
> **Dependencies:** Phase 2.1  
> **Status:** Not started

## Goal

Cross-check Jackson 3 writer fixtures against a pinned JSON:API 1.1 draft schema without treating that unreleased schema as the conformance authority.

## Research and constraints

- [JSON:API FAQ](https://jsonapi.org/faq/) links a schema, but the [1.1 schema issue](https://github.com/json-api/json-api/issues/1672) and [schema publication PR](https://github.com/json-api/json-api/pull/1750) remain open; no released official JSON:API 1.1 schema exists as of this plan.
- [JSON:API 1.1 schema PR #1603](https://github.com/json-api/json-api/pull/1603) is open and therefore mutable. Pin its contributor-fork head commit `4ee1c644fcc273044ecec39a6b8c0f0485abdc0e`, record the PR and source provenance, and call the files “JSON:API project's draft-PR schemas,” not “official schemas.”
- The pinned draft contains separate Draft 2020-12 schemas for responses, create-resource requests, update-resource requests, and update-relationship requests; fixtures must select the matching document usage rather than applying the response schema globally.
- The textual [JSON:API v1.1 specification](https://jsonapi.org/format/1.1/), core validation, and repository positive/negative fixtures remain authoritative because a permissive or incomplete schema can produce false positives.
- At implementation, use `com.networknt:json-schema-validator:3.0.6`, which supports JSON Schema
  Draft 2020-12 on Jackson 3; keep it test-only and regenerate dependency-verification metadata for
  the pinned version.

## Deliverables

- Vendor the four pinned draft schema files under `fixtures/jsonapi-schema/1.1-pr1603/` with commit URL, retrieval date, SHA-256 values, draft status, and upstream CC0 provenance in an adjacent README; configure only test resources to consume them.
- Add `com.networknt:json-schema-validator:3.0.6` as `testImplementation` only and a focused schema
  harness that never performs network access during tests.
- Classify Phase 2.1 generated fixtures as response, create-resource, update-resource, or update-relationship documents and validate each against the corresponding pinned schema.
- Add invalid control fixtures for every schema kind so a broken/no-op harness fails, and document schema disagreements as explicit allow-listed cases with links to the governing textual rule or upstream issue.
- Update `docs/conformance.md` with the supplemental cross-check and its limitations; do not change a feature status solely because the draft schema accepts it.

## Non-goals

- Publishing, repairing, or claiming ownership of the JSON:API schema.
- Calling the pinned draft an official or complete JSON:API 1.1 conformance oracle.
- Runtime schema validation or a production dependency on a JSON Schema engine.
- Replacing focused writer, reader, malformed-input, or aggregate-validation tests.

## Implementation boundaries

- Tests load immutable classpath resources and fail if their recorded SHA-256 values change. Updating the pin requires an intentional diff of all four schemas, provenance metadata, and fixture results.
- Validate bytes generated by the public Phase 2.1 writer, not hand-authored copies of expected output.
- Schema success is supplemental evidence only. A conflict with the textual specification is recorded and tested according to the specification, never “fixed” by weakening production behavior to satisfy the draft.
- Keep schema-engine transitives off all published runtime and API configurations; ArchUnit production allowlists do not gain schema-validator packages.

## Test strategy

- Parameterize positive generated fixtures by schema kind and report fixture path plus validator messages on failure.
- Include at least one known-invalid control for each schema kind and assert the expected failing keyword/location so the harness itself is tested.
- Verify offline execution and inspect Gradle runtime/API dependency reports to prove the validator is test-scoped.

## Acceptance criteria

- [ ] All four schemas are pinned to commit `4ee1c644fcc273044ecec39a6b8c0f0485abdc0e` with verified hashes, provenance, draft labeling, and no test-time network access.
- [ ] Every applicable Phase 2.1 generated fixture passes its usage-specific draft schema, while one invalid control per schema kind proves the harness rejects malformed documents.
- [ ] Any draft/spec disagreement is explicit and linked; schema acceptance alone never establishes a conformance status.
- [ ] The schema validator and its transitives are absent from published API/runtime configurations, and dependency-verification metadata is updated.
- [ ] `./gradlew :jsonapi-java-jackson3:test --tests '*JsonApiDraftSchemaSpec'` passes.
- [ ] `./gradlew clean build` passes.
- [ ] Spotless passes (`./gradlew spotlessApply` then `./gradlew spotlessCheck`).
- [ ] Sonar Quality Gate passes; if `SONAR_TOKEN` is unavailable, report Sonar blocked and that CI must still pass the gate.
